## Conclusions

What we learned is that there are some interesting ideas that need to be incorporated to a lab data transformation script, and several important details at play for a processing script --> synthetic data gen script. 

1. Must be in the converter

Rows are the truth, times are not. The painted frames equal the rows, and the event times are shifted in 33 sessions. All run extents and durations come from frames. Durations from event times are the wrong layer of abstraction at this point.

- Runs need cleaning before they're translatable. I.e. duplicates and so forth.
- Epochs are by role, with timestamps. The roles are arena, track and variant. The tag lookup supplies environment and condition. The cases to handle are an absent arena, an epoch-less session (NS14_rec14) and about 37 runs outside every stamp, this oculd be false starts, or an epoch issue. A data vis here would really help.

I believe the head-direction offset uses the midpoint of the two lights and a 30 px/s?? floor.

FOr synthetic data we will need to subset the data along several axis. We need to pick sessions by baseline condition, rat, and tracking quality. Infusion and dark conditions apply to the whole file, and rotation variants are a different layout. A baseline-only default for fitting statistics is the safe one. The columns it needs are protocol, exclude, the unfilled fractions, and maybe n_clean_runs on sessions.csv. these can be worked out post transfor though and will need more robust EDA to develop a working subset.

### What the data can support

There are about 14,000 clean and 5,300 dirty labeled track runs, with a path id on every one. The arena has no labeled structure at all: 0 run events in 109 sessions. A statistical generator can be fit to track runs by path. The arena can only be fit from raw frames, as foraging. 


Order and gaps are releavnt as well... path sequence and the between intervals (400 to 1000 or more frames) come from the sorted run order. Duplicates would have created fake zero-length gaps and double counts, so the cleaning rules matter for synthetic data  generation. 27% of runs are dirty so the question becomes do we fit the generator on clean runs only and or validate against both...

Need to determine still if tracks comparable across sessions? We know arena and track differ, and rotated variants differ. We never compared track footprints across days, and the scale is only a rough 3.3 px/cm. Pooling statistics needs one shared frame. This is one of the first thing to look at after the transformer. We need top know if runs act as a same-path from different sessions overlay in camera pixels. Path ids and heading encode travel direction. They are fine as validation labels and aggregate statistics. But the synthetic training input has to be positions only. at least as of now. Any heading-based statistic used to build the generator needs a control for this.


Not needed n the transform step are: resampling, registration, scale estimates, smoothing, speed columns and per-run quality columns. The stats stage can compute all of these from `frames.run`. Indecision counts? these could be an int calculated after this step as well. The only choices here that need a baseline-only default for fitting, the optional n_indecision column, and what sets exclude. But maybe we do not need this at all?
